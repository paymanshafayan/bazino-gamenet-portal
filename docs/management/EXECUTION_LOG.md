# اجرای پلن توسعهٔ مدیریت — ۲۰۲۶/۰۹/۰۵

مجوز اجرا: درخواست صریح کاربر برای اجرای پلن تأییدشده و کنارگذاشتن موقت اتصال سخت‌افزاری POS.

## وضعیت

اجرای batchها آغاز شد. نتیجهٔ هر batch پس از تست در همین سند ثبت می‌شود؛ این عنوان به معنی تکمیل همهٔ قابلیت‌ها نیست.

## خارج از اجرا

- کنترل/تستر سخت‌افزار POS و تراکنش واقعی بانکی.
- SMTP، فعال‌سازی PayTR یا درگاه آنلاین.
- انتشار زنده یا مصرف اعتبار Manus/Zernio بدون اتصال/اجازهٔ معتبر.

## Batch 1 — زیربنا

- رکوردهای عملیاتی نسخه‌دار مستقل از blob، تراکنش بومی در سه provider و سری‌کردن دسترسی SQLite در await؛ CAS و نگاشت یک‌به‌یک. Mongo برای تراکنش مالی به replica set نیاز دارد؛ تست واقعی این موتور و SQL Server هنوز انجام نشده.
- ورود واقعی مدیریت با JWT/مجوز سمت سرور؛ صفحهٔ نگاشت ایستگاه و مدیریت دسترسی حساب‌ها.
- قرارداد رزرو با وضعیت مالی/حضور مجزا؛ رد/تأیید قدیمی دیگر check-in ایجاد نمی‌کند. حفظ reservationId در نتیجهٔ تسویه.
- خطای نحوی موجود در HEAD در انتهای `Management App/Bazino/src/App.tsx` (دنبالهٔ تکراری `dleAddTariff`) هنگام اولین lint واقعی مدیریت پیدا و حذف شد.
- آزمون این batch: ۸/۸ تست core/SQLite؛ TypeScript هر دو پروژه و build مدیریت موفق؛ API ناشناس 401، ورود/دادهٔ معتبر 200. Chromium واقعیِ ورود و واردکردن ایستگاه‌ها اجرا شد؛ دو تصویر تمام‌صفحه `batch1-login.png` و `batch1-mapping.png` با read_file بازبینی شدند.

## Batch 2 — دریافت وجه و کیف پول

- دریافت نقدی/POS با تأیید صریح اپراتور، رسید جدا و کلید یک‌باراجرا؛ POS همچنان ثبت دستی و بدون ارتباط بانکی.
- موجودی با جمع دفترکل خوانده می‌شود؛ شارژ و رسید در یک تراکنش ثبت می‌شوند. نقدکردن دو مرحله دارد: رزرو موجودی، سپس تأیید تحویل نقد؛ لغو پیش از تحویل با برگشت مبلغ.
- مسیرهای مالی قدیمی نمی‌توانند روش سوم/برداشت بی‌هویت را دور بزنند؛ UI کیف پول سایت و مدیریت یک کامپوننت مشترک دارند. صف محلی قدیمی دیگر منبع تأیید نقدکردن نیست.
- تست: ۱۳/۱۳ core/SQLite شامل رقابت برداشت، تکرار درخواست، rollback و حفظ reservationId؛ TypeScript هر دو برنامه و build مدیریت موفق. Chromium واقعی: انتخاب POS دستی، ثبت شارژ، نمایش رسید و رزرو نقدکردن؛ سه تصویر batch2 با read_file بازبینی شدند. یک 401 مورد انتظار قبل از ورود در لاگ مرورگر دیده شد؛ خطای JS گزارش نشد. تست سرویس بانکی انجام نشده است.

## Batch 3 — رزرو روی ایستگاه و سانس معتبر

- رزروهای پرداخت‌شده/در انتظار از order→reservation معتبر روی کارت نگاشت‌شده نمایش داده می‌شوند؛ حضور، شروع و دریافت وجه جدا هستند. تاریخ‌های جدید به UTC/روز مجموعه تثبیت شدند.
- سانس‌ها، pause/resume، انتقال، تغییر تعرفهٔ مجاز، تمدید و پایان روی بک‌اند ثبت می‌شوند. هزینهٔ پوشش‌داده‌شده توسط رزرو دوباره دریافت نمی‌شود؛ quote زمان صورتحساب را ثابت می‌کند. دادهٔ نمونهٔ جدید به‌عنوان سانس واقعی فعال شروع نمی‌شود.
- ثبت مستقیم قدیمی سایت به checkout مشترک در محل هدایت شد؛ checkout کیف پول سایت محفوظ و کلید یک‌باراجرا در مودال سایت اضافه شد.
- تست: ۱۷/۱۷ core/SQLite، TypeScript و build مدیریت؛ API واقعی ساخت رزرو کیف‌پولی و پرداخت حضوری در دو ایستگاه؛ Chromium نمایش روی کارت درست و شروع رزرو پرداخت‌شده (صفر خطای ثبت‌شده). تصاویر batch3 با read_file بازبینی شدند.

## Batch 4 — کافه و فروشگاه

- دو تب مستقل با صف آنلاین/حضوری، فرم سفارش، کاتالوگ/موجودی، فیلتر و ارتباط ایستگاه/سانس؛ همین نماها در بخش موجود کافه/فروشگاه ادمین سایت استفاده می‌شوند.
- سفارش قبل از پرداخت دیده می‌شود؛ پذیرش کالا را یک بار تخصیص می‌دهد و دریافت مجدد موجودی کم نمی‌کند. لغو قبل از آماده‌سازی، تخصیص را آزاد می‌کند؛ ضایعات و مرجوعی کامل دارای تأیید/علت‌اند.
- کاتالوگ نمونه هنگام تخصیص materialize می‌شود و مقدار DB بر نمونه مقدم است؛ شناسهٔ فعال سفارش‌ها UUID شد. انتخاب ایستگاه واقعی به فرم سایت افزوده شد، بدون حدس از متن میز.
- تست: ۱۹/۱۹ core/SQLite؛ TypeScript و build مدیریت. API واقعی: دو درخواست برای آخرین کالا → یکی موفق و یکی 409، بعد از پرداخت موجودی همچنان صفر؛ سفارش آنلاین کافه روی st-1 و سانس صاحب حساب مشاهده شد. سه نمای صف کافه/فروشگاه و کاتالوگ در Chromium بدون خطای ثبت‌شده، تصاویر با read_file بازبینی شدند.

## Batch 5 — افیلیت و گزارش صندوق

- تب همکاری در فروش از موتور موجود استفاده می‌کند: CRUD با کنترل نسخه، نرخ‌های ارث‌بری، ثبت معرفی حضوری، گزارش/کمیسیون و کیف پول همان همکار. کیف پول به جزئیات همکار در ادمین سایت نیز افزوده شد؛ کمپین Instagram قبلی حفظ شده است.
- تأیید/واریز کمیسیون در تراکنش اتمیک اجرا می‌شود؛ گزارش جدید فروش را از شارژ کیف پول و تحویل نقد جدا می‌کند. تعهد مشتری شامل موجودی و مبالغ در انتظار تحویل است؛ CSV و رسیدهای قابل چاپ اضافه شدند.
- در بازبینی این مرحله مشخص شد whitelist قدیمی onsite_orders، payload را نادیده می‌گرفت؛ برای حفظ اتصال/وضعیت انبار افزوده شد. همچنین resolver قدیمی نمونه بر قیمت/موجودی DB مقدم بود؛ تقدم به رکورد واقعی داده شد. این تغییر در رگرسیون نهایی دوباره سنجیده می‌شود.
- تست: ۲۲/۲۲ core/SQLite شامل واریز تکراری کمیسیون و عدم شمردن شارژ به‌عنوان فروش؛ TypeScript و build مدیریت موفق. API گزارش و اتصال کیف پول همکار، Chromium و دو تصویر batch5 بازبینی شدند. سلکتور exact هارنس گزارش ابتدا timeout شد؛ سلکتور اصلاح و تصویر گزارش گرفته شد؛ در اجرای اصلاح‌شده خطای مرورگر ثبت نشد.
