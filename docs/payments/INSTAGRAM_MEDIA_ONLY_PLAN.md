## ۱. مسئولیت‌ها و جریان قطعی

```text
ناشر بیرونی (امروز Manus): محتوای مصوب → فقط Instagram media_id ──┐
                                                                ├→ registry مشترک رسانهٔ مصوب
پنل بازینو → Publishing Service → Zernio API → نتیجهٔ انتشار ────┘
                          ↓
Backend: رسانهٔ منتشرشده در کمپین/حساب مجاز، مستقل از ناشر
                          ↓
Zernio: comment.received → امضا + حساب + تطبیق media_id
                          ↓
کامنت کلیدواژهٔ همکار → یک PR توضیحی + دکمهٔ Follow
                          ↓
message.received دکمهٔ همان همکار → DM کد عددی + متن آماده؛ بدون لینک دعوت
                          ↓
کامنت همان کد توسط دوست دیگری زیر همان رسانه
                          ↓
share_confirmed_by_friend_code → یک PR درخواست Follow برای دوست
                          ↓
message.received دکمهٔ همان دوست → حداقل Gate → DM لینک خصوصی فقط به دوست
                          ↓
Gate سایت: رضایت + ورود/ثبت‌نام موجود + شروط policy → کوپن اختصاصی یک‌بارمصرف
                          ↓
انتساب سمت سرور → رزرو/حضور پرداخت‌شدهٔ واجد شرایط → Pending → تأیید/تسویه
```

- Manus، در این قرارداد افیلیت، **شناسهٔ شریک نمی‌فرستد، کد/لینک نمی‌سازد، دایرکت را مدیریت نمی‌کند و کوپن/کمیسیون را تعیین نمی‌کند**. این محدودیت به معنای حذف قابلیت مستقل تولید محتوا با Manus از کل محصول نیست.
- Zernio واسط دریافت تعامل و ارسال PR/DM است و در حالت انتشار داخلی، API نشر را نیز تأمین می‌کند؛ موتور مستقل Comment-to-DM موازی برای همین کمپین فعال نمی‌شود. تولید محتوا، انتشار و تصمیم افیلیت سه مسئولیت جدا هستند؛ وضعیت دامنه فقط در بک‌اند بازینو است.
- لینک دعوت خصوصیِ این چرخه به همکار تحویل داده نمی‌شود: نه در پیام، دکمه/ضمیمه، پرامپت Manus، خروجی قابل‌مشاهدهٔ همکار یا لاگ. لینک عمومیِ حرفه‌ایِ Creator، در صورت مجازبودن، نوع جداگانه دارد و جای لینک خصوصی دوست نیست.

## ۲. رفع صریح تعارض‌های داخل سند — پیشنهاد اجرایی این پلن

تأیید این پلن شامل تصمیم‌های زیر است؛ این‌ها نباید به‌صورت پنهان به متن اصل سند نسبت داده شوند:

| تعارض/ابهام | تصمیم پیشنهادی |
|---|---|
| شرح مرحله‌ای §۲ در برابر دیاگرام خلاصهٔ §۸ که کد را در PR می‌گذارد | **شرح به‌روز §۲ مقدم است**: PR اول فقط توضیح و دکمه؛ کد در DM دوم پس از تعامل. برای دوست نیز لینک در DM پس از Gate، نه PR دومِ همان کامنت |
| کلیدواژهٔ `SQUAD` در جدول قدیمی §۶ در برابر کلیدواژه‌های جدید | چهار کلیدواژهٔ `آماده / Hazır / Ready / Готово` ملاک نسخهٔ جدیدند؛ `SQUAD26` شناسهٔ کمپین است. `SQUAD` فقط با فعال‌سازی صریح ادمین به‌عنوان alias مجاز می‌شود |
| «زبان کلیدواژه» در برابر «زبان پست» | رسانه، زبان‌های مجاز دارد. در پست چهارزبانه، کلیدواژه زبان مکالمه را تعیین می‌کند؛ کپشن ترکی آن را override نمی‌کند. در Reel تک‌زبانه فقط زبان مجاز همان Reel فعال است. کامنت عددی دوست زبان ثبت‌شدهٔ دعوت همکار را می‌گیرد. هیچ fallback خودکار به زبان دیگر انجام نمی‌شود |
| یک کامنت با چند کلیدواژهٔ چندزبانه | `ambiguous_language`، بدون پاسخ خودکار؛ ادمین می‌تواند در مهلت مجاز یک زبان تعیین کند. تغییر زبان/ویرایش کامنت، مجوز PR دوم نیست |
| `comment_id + campaign_id + language` در برابر سقف یک PR | کلید dedup سند حفظ می‌شود، ولی قید قوی‌تر **یک PR برای account + commentId در همهٔ زبان‌ها/کمپین‌ها** نیز وجود دارد |
| Like در نمودار §۸ الزامی است ولی در فلو تفصیلی §۲ گام ندارد | حداقل دریافت لینک: کامنت معتبر دوست + گیت Follow طبق سطح اثبات مجاز. **پیشنهاد برای فعال‌سازی کوپن: Like به‌صورت خوداظهاریِ صریح در Gate سایت لازم باشد**؛ هرگز `like_verified` از روی checkbox ساخته نشود. ادمین policy را پیش از فعال‌سازی تأیید می‌کند |
| «فقط مشتری جدید» در §۱ در برابر درصد مشتری بازگشتی در جدول پیشنهادی | برای این کمپین، پیش‌فرض صلاحیت **مشتری جدید** است؛ نرخ/پاداش بازگشتی، تورنومنت و override خودکار فعال نمی‌شوند مگر با policy مالیِ صریح. نرخ‌ها و مبالغ نمونه، تصمیم مالی مصوب تلقی نمی‌شوند |
| پیشنهاد بتای دستی در §۹ در برابر درخواست مستقیم اتوماسیون | MVP خودکار روی بک‌اند فعلی، با حالت دریافت/آزمایش و rollout کنترل‌شده؛ بتای دستی شرط اجباریِ شروع توسعه نیست |

**محدودیت‌های روشن:** Zernio برای Private Reply سقف یک پیام برای هر کامنت و مهلت هفت‌روزه دارد؛ پیام دوم باید از مسیر DM و در پنجرهٔ مجاز ارسال شود. دکمهٔ inline postback برای PR استفاده می‌شود؛ ارسال مجدد PR راه‌حل خطای DM نیست. [2](https://docs.zernio.com/platforms/instagram) [1](https://docs.zernio.com/changelog)

Follow بدون رضایت/سابقهٔ پیام ممکن است `unknown` باشد؛ نبود سیگنال نه «فالو ندارد» است نه «فالو تأیید شد». `follow_verified` فقط از شاهد معتبر سمت سرور؛ `button_event_only`/`self_attested` فقط مطابق policy مصوب. پاسخ صریح منفی، `unknown` یا خطای شبکه با یک boolean مبهم مخلوط نمی‌شوند. [2](https://docs.zernio.com/platforms/instagram)

Share فردی در این پلن همان **شاهد غیرمستقیمِ مصوب کامنت کد توسط دوست** است؛ منتظر رویداد Share فردی نمی‌مانیم و دادهٔ Media Insights را به یک شخص نسبت نمی‌دهیم. Like فردی با API در این طراحی تأییدشده فرض نمی‌شود. اگر شرایط/دسترسی لازم فراهم نباشد، وضعیت pending/نیازمند اقدام با علت واقعی ثبت می‌شود؛ عبور موفق جعلی ممنوع است.

## ۳. قراردادهای API و تطبیق شناسه‌ها

### ۳٫۱ Manus → ثبت رسانه، فقط یک دادهٔ تجاری

از مسیر موجود استفاده می‌شود:

```http
POST https://bazino.pro/api/integrations/instagram/published-media
Authorization: Bearer <TOKEN_WITH_MEDIA_INGEST_SCOPE>
Content-Type: application/json
Idempotency-Key: instagram:<INSTAGRAM_MEDIA_ID>

{"media_id":"<INSTAGRAM_MEDIA_ID>"}
```

- `media_id` رشته است؛ هرگز به Number تبدیل نمی‌شود. منظور ID رسانهٔ منتشرشدهٔ اینستاگرام است، نه ID داخلی رکورد Zernio، permalink/shortcode، commentId یا author.id.
- auth و idempotency، هدرهای امنیتی‌اند؛ Manus دادهٔ شریک، کد ارجاع یا لینک خصوصی در بدنه نمی‌فرستد و چنین خروجی‌ای هم نمی‌گیرد.
- کمپین/حساب از پیکربندی یا scope توکن سمت سرور مشخص می‌شود؛ ثبت صرفِ ID به معنی تأیید تمام metadata یا شروع ارسال نیست. نوع/زبان/نسخهٔ محتوای لازم از رکورد معتبر بک‌اند یا تنظیم رسانه تکمیل می‌شود. در نبود دادهٔ لازم، `needs_review`؛ **نه حدس post به‌جای reel یا زبان ترکی به‌جای زبان ناشناخته**.
- قرارداد قدیمیِ دارای `media_type` فقط برای سازگاری معتبر می‌ماند؛ بدنهٔ حداقلی بالا واقعاً باید پذیرفته شود. `published_at` ناشناخته با زمان دریافت اشتباه نشود؛ `receivedAt` مستقل ثبت شود.
- پاسخ فقط نتیجهٔ ثبت: شناسهٔ رسانه/کمپین و `registered|needs_review`، همراه `duplicate`؛ بدون code/invite_url. تکرار همان ID همان رکورد را می‌گیرد و رسانهٔ لغوشده را خودکار دوباره فعال نمی‌کند.
- رسانه‌های مجاز یک registry ماندگار هستند، نه یک `TEST_MEDIA_ID` هاردکد یا متغیر «آخرین پست»؛ ثبت Reel تازه، پست مجاز قبلی را ناخواسته کنار نمی‌گذارد. در هر لحظه نگاشت مؤثر media→account/campaign/policy یکتا و مشخص است.

### ۳٫۲ Zernio → گیرندهٔ ثبت‌شدهٔ کاربر

```text
POST https://bazino.pro/api/webhooks/zernio
GET  https://bazino.pro/api/webhooks/zernio/health
```

- URL اصلی تغییر نمی‌کند؛ مسیر قبلی `/api/integrations/zernio/webhook` با همان دفتر دریافت و dispatch مشترک حفظ می‌شود، بدون دو پردازشگر مستقل.
- مسیر جدید: HMAC الزامی با `ZERNIO_WEBHOOK_SECRET`، روی raw body و مقایسهٔ زمان‌ثابت؛ Bearer عمومی جایگزین امضا نمی‌شود. مسیر قدیمی نیز نباید راه دورزدن scope ناشر باشد: اگر سازگاری Bearer حفظ شود، فقط توکنِ صریحاً مجاز برای webhook، نه توکن ingest/Manus. توکن‌های قدیمی با طبقه‌بندی و مهاجرت مستند تعیین تکلیف می‌شوند؛ سازگاری به معنی مجوز همگانی همهٔ توکن‌ها نیست.
- parser محدود پیش از JSON عمومی، schema رویداد، حساب متصل مجاز `ZERNIO_IG_ACCOUNT_ID` و platform=instagram کنترل می‌شوند. حساب `@bazinopro` با ID اتصال ثبت‌شده شناسایی می‌شود، نه صرف متن username.
- adapter، شکل اعلام‌شدهٔ کاربر (`postId/mediaId`, `commentId`, `author.id`, متن) و envelope رسمی `comment/post/account` را به DTO مشترک تبدیل می‌کند. ID داخلی Zernio در `post.id` بدون تشخیص نوع، Instagram media id فرض نمی‌شود؛ فیلدهای متعارض به‌جای انتخاب بی‌صدای اولین مقدار رد/قرنطینه می‌شوند.
- شرط لازم پردازش کامنت:

```text
signatureValid
AND accountId == configuredBazinoAccount
AND normalizedInstagramMediaId == approvedRegistryNativeMediaId
AND media.active AND campaign.active AND policy.ready
```

- تطبیق باید **دقیق** باشد؛ نه شامل‌شدن متن، نه prefix یا مقایسهٔ commentId با mediaId. author.id شناسهٔ شرکت‌کننده است و فقط برای هویت همکار/دوست مصرف می‌شود.
- کامنت رسانهٔ ثبت‌نشده یا حساب دیگر: پاسخ کنترل‌شدهٔ ignored و **صفر PR/DM/کد/کوپن**. وب‌هوک زودتر از ingest نیز اجازهٔ پردازش ندارد؛ فقط می‌تواند برای تطبیق مجددِ محدود، پس از ثبت و تأیید همان رسانه، در وضعیت انتظار بدون اثر تجاری نگه‌داری شود.
- `webhook.test` معتبر: پاسخ موفق با `outboundSent:false` و بدون اثر تجاری. اشتراک Zernioِ ساخته‌شده، به‌تنهایی اثبات استقرار این مسیر نیست.
- **نسخهٔ ۲:** dispatcher همین مسیر، خانواده‌های Post / External / Account / Message / Comment را جدا پردازش می‌کند؛ گیت رسانهٔ بالا برای فلو افیلیت است، نه شرطی که post.scheduled یا account.disconnected را به علت نداشتن Media ID رد کند. مالکیت global post event از job/targets معتبر استخراج می‌شود. فقط نتیجهٔ منتشرشدهٔ یک job مصوب خودمان یا ingest معتبر، registry را برای کمپین مجاز می‌کند؛ external discovery به‌تنهایی مجوز نیست.
- فهرست اصلی ۲۳ رویداد در سند معماری است. `analytics.synced` برای subscription جدا و مسیر پیشنهادی `/api/webhooks/zernio/analytics`، با ثبت سریع و worker کم‌اولویت طراحی می‌شود؛ هنوز آن مسیر مستقر نشده و ساخت subscription دوم قبل از آماده‌شدن لازم نیست.

### ۳٫۳ دکمه‌ها و پیام دوم

**رویداد کامنت به‌تنهایی کافی نیست.** همان اشتراک باید `comment.received` **و** `message.received` داشته باشد. payload دکمه از metadata رسمی (`postbackPayload`/`quickReplyPayload`) و context گفتگو استخراج می‌شود؛ نه فقط `body.button`. Zernio این تعامل‌ها را در metadata پیام مستند کرده است. [1](https://docs.zernio.com/changelog)

- دکمه با token غیرقابل‌حدس/امضاشده به member، role، campaign، media و policy متصل است. `sender.id` واقعی وب‌هوک باید با شرکت‌کنندهٔ همان مرحله برابر باشد؛ دانستن memberId مجوز پیش‌برد Gate شخص دیگر نیست.
- در DM، mediaId الزاماً در رویداد نیست؛ رابطه از دکمهٔ معتبر و وضعیت ذخیره‌شده بازیابی می‌شود. این مسیر نباید مجوز رسانه را دور بزند.
- مسیر DM مطابق قرارداد conversation-based تنظیم می‌شود: `/v1/inbox/conversations/{conversationId}/messages`؛ conversation/recipient به همان حساب/کاربر تطبیق داده می‌شود. مسیر فعلی `/v1/inbox/messages` بدون تطبیق حفظ نمی‌شود. [1](https://docs.zernio.com/changelog)
- ارسال خودکار فقط داخل پنجرهٔ معمول مجاز؛ از برچسب HUMAN_AGENT برای دورزدن محدودیت پیام تبلیغاتی استفاده نمی‌شود. بیرون پنجره یا بدون interaction معتبر، pending/manual action؛ نه PR دوم یا ارسال انبوه.

## ۴. ماشین حالت و جلوگیری از نشت لینک

| ورودی معتبر | تغییر حالت | تنها خروجی مجاز |
|---|---|---|
| کلیدواژهٔ همکار روی رسانهٔ مجاز | `partner_follow_pending`؛ زبان و policy ثابت | یک PR با متن اول همان زبان و دکمه؛ بدون لینک خصوصی و بدون کدِ پیش از Gate |
| دکمهٔ همان همکار + Gate مطابق policy | `partner_code_ready` → پس از پاسخ معتبر provider: `partner_code_sent` | DM پیام دوم شامل کد و متن آماده؛ **هیچ invite_url، دکمهٔ URL خصوصی یا ضمیمهٔ حاوی لینک** |
| کد معتبر توسط دوستِ دیگری زیر همان media/campaign | `friend_follow_pending` و `share_confirmed_by_friend_code` | یک PR متن دوست + دکمه؛ بدون لینک تا تکمیل حداقل Gate |
| دکمهٔ همان دوست + حداقل Gate | `friend_link_ready` → پس از ارسال معتبر: `friend_link_sent` | DM لینک خصوصی و راهنمای فعال‌سازی، فقط به همان دوست |
| بازکردن لینک + رضایت + ورود موجود + policy کامل | `friend_activated` / `coupon_issued` | کوپن اختصاصی همان کاربر، اتمیک و یک‌بارمصرف |
| پرداخت/حضور واجد شرایط | `commission_pending` | ثبت در موتور مالی موجود؛ بدون کمیسیون برای تعامل اجتماعی |

- ثبت `sent` قبل از پاسخ معتبر provider ممنوع است؛ accepted/sent/delivered/read تفکیک می‌شوند و فقدان رسید تحویل، delivered محسوب نمی‌شود.
- کد یکتا با قید DB و retry محدودِ امن ساخته می‌شود؛ fallback مبتنی بر timestamp که ممکن است تکراری باشد حذف می‌شود. عضویت/کد تکراری برای همان شریک در scope مصوب ایجاد نشود؛ دوست فقط کدی را مصرف می‌کند که برای همان رسانه/کمپین صادر و فعال شده است.
- همکار نمی‌تواند کد خودش را به‌عنوان دوست ثبت کند. کد در رسانه/کمپین دیگر پذیرفته نمی‌شود؛ عدد داخل متن نامرتبط، بدون سیاست روشن، کد دوست تلقی نمی‌شود. نرمال‌سازی ارقام فارسی/عربی/لاتین و صحت کل عدد تست می‌شود.
- زبان از نخستین رویداد معتبر ثابت می‌ماند؛ نسخهٔ policy و template برای ادامهٔ همان مکالمه snapshot می‌شوند. ویرایش متن ادمین، مکالمهٔ نیمه‌تمام را بی‌صدا تغییر نمی‌دهد.
- اصل هشت متن همکار در فایل منبع محفوظ است؛ نسخهٔ پایهٔ پیام فارسی دوم، با تمام عبارت‌های آن، snapshot-test می‌شود و فقط `[عدد یکتا]` با کد جایگزین می‌شود. تغییر مجاز ادمین، نسخهٔ تازهٔ template با تأیید جدا ایجاد می‌کند؛ متن منبع و نسخهٔ پایه بازنویسی نمی‌شوند. برای متن دوست/لینک که در سند عبارت کامل چهارزبانه ندارد، الگوهای موجود بازبینی و برای تأیید ادمین preview می‌شوند؛ متن جدید به‌عنوان نقل دقیق سند معرفی نمی‌شود.
- ویرایشگر پیام همکار فقط متغیرهای مجاز نقش را قبول می‌کند؛ `invite_url` و لینک خصوصیِ hardcoded یا قرارگرفته در buttons/attachments رد می‌شوند. تولید لینک وظیفهٔ سرویس friend است، نه helper عمومی ساخت partner.
- پرامپت فعلی پنل که می‌گوید «Send the invite_url to the partner» و قرارداد بیرونی `partner-invite` اصلاح/محدود می‌شوند. توکن Manus فقط ingest؛ داده‌ها و لینک‌های تاریخی بدون مهاجرت کنترل‌شده پاک یا بازتولید نمی‌شوند.

## ۵. Friend Gate سایت و کوپن

- لینک خصوصی، token غیرقابل‌حدس/امضاشده و scope دوست/کمپین/رسانه دارد. secret امضای آن مستقل از Webhook Secret می‌شود؛ کلید مؤثر قبلی پیش از انتقال تثبیت و لینک‌های تاریخی کنترل‌شده حفظ می‌شوند.
- صفحهٔ Gate واقعی در سایت، مستقل از theme-overrides و متصل به ورود/OTP موجود، ایجاد/تکمیل می‌شود: رضایت ثبت handle، نمایش سطح اثبات و شرایط دقیق، ثبت Like به‌صورت self-attested در policy پیشنهادی و claim کوپن پس از احراز شرایط.
- داشتن لینک و ورود با OTP به معنی اثبات مالکیت حساب اینستاگرام نیست؛ روش `link_possession`/رضایت جدا از `follow_verified` ثبت می‌شود. رمز عبور Instagram یا توکن Meta از کاربر گرفته نمی‌شود.
- صدور کوپن با کلید یکتای campaign + friend/site-user و اتصال owner به حساب سایت، در تراکنش انجام می‌شود؛ دو درخواست هم‌زمان دو کوپن نسازند. **کوپن مشترک فعلی `SQUAD-${partnerCode}` برای همهٔ دوستان یک همکار استفاده نمی‌شود**.
- تعداد استفاده، دامنهٔ مصرف، تاریخ، مبلغ/درصد و حداقل خرید از تنظیمات مصوب سایت؛ هیچ جایزهٔ تأییدنشده از متن نمونه فعال نمی‌شود. اگر کوپن خاموش/مقدار صفر است، پیام وعدهٔ فعال‌بودن کوپن ندهد.
- token/link خصوصی از log، analytics عمومی، Referer به سرویس ثالث و خروجی همکار حذف/پوشانده شود. اگر برای outbox لازم است، دسترسی و ذخیرهٔ آن محدود و محافظت‌شده باشد؛ `token` مدل سند به معنای ثبت API Key/Secret در audit نیست.

## ۶. داده، صف و مالی — روی زیربنای موجود

### نگاشت مدل مفهومی، نه ساخت دیتابیس موازی

- `affiliates`، `ig_media`، `ig_members`، `ig_events`، coupons، attribution، reservations/orders، commissions و wallet موجود بازاستفاده شوند.
- metadata کمپین/زبان/policy، consent/follow/like evidence، tracking link، inbox/outbox و unique claims در OpsRecords نسخه‌دار/رکوردهای مناسب همان `IDataStore` تکمیل شوند؛ هر migration لازم در هر سه provider و با حفظ داده انجام شود. MySQL/Drizzle و ورود/پنل Manus داخل ZIP وارد سایت نمی‌شوند.
- invariant مالی/کوپن با تراکنش و uniqueness واقعی اجرا شود؛ اتکا به «اول بخوان، بعد بنویس» یا حافظهٔ یک process کافی نیست.

### inbox/outbox

- event id پایدار + account + hash بدنه؛ dedup منطقی comment/campaign/language؛ قید مستقل یک PR برای هر کامنت.
- claim اتمیک، lease worker، retry با backoff و سقف زمانی، بازیابی restart و kill-switch کمپین. دریافت webhook پس از ذخیرهٔ پایدار سریع پاسخ دهد؛ fetch خارجی داخل تراکنش طولانی DB نباشد.
- در timeout با احتمال ارسال، `delivery_unknown`؛ ارسال کور تکرار نشود. وضعیت از provider/گفتگو تطبیق یا برای اقدام مدیر نگه‌داری شود. exactly-once مطلق برای شبکه ادعا نمی‌شود.
- rate limit و مهار تکرار عمدی همان شرکت‌کننده؛ ورودی نامعتبر/حساب نامجاز پیش از اثر تجاری رد شود. لاگ حداقلی با retention مشخص، بدون متن کامل خصوصی/سکرت به‌صورت پیش‌فرض.

### انتساب و کمیسیون

- آخرین لینک معتبر با ثبت سمت سرور، تا پنجرهٔ مصوب؛ کد دستیِ آگاهانهٔ فرم بر لینک مقدم. اگر کد دستی نامعتبر است، به کد قبلی بی‌صدا برنگردد؛ خطا/تصمیم روشن باشد.
- `newCustomer` از سابقهٔ مرجع و تعریف مصوب محاسبه شود، نه ادعای کاربر یا عمر کوکی. کارکنان/خودارجاعی/تکرار/تست/لغو و refund کنترل و علامت‌گذاری شوند.
- برای کمپین جدید، یک تراکنش یک صاحب کمیسیون دارد؛ پاداش لایه‌ای/override مستقل خودکار اضافه نشود. رزرو پیش‌پرداخت‌شده و پرداخت سانسِ مرتبط دو فروش مستقل از همان مبلغ شمرده نشوند.
- رزرو آنلاین و حضور/سانس پرداخت‌شدهٔ حضوری به همان موتور وصل شوند؛ الان `onOrderPaid` فقط reservation/tournament را می‌پذیرد و تطبیق session/walk-in لازم است. روش‌های دریافت حضوری نقدی/POS دستی باقی می‌مانند.
- `Pending` تا پایان مهلت مصوب بازپرداخت و سپس تأیید واجد شرایط؛ لغو/بازپرداخت، برگشت قابل‌حسابرسی ایجاد کند. واریز اعتبار کیف پول، تحویل نقد واقعی و «تسویهٔ ماهانه» به‌عنوان یک رویداد واحد یا پرداخت بانکی خودکار گزارش نشوند.
- نرخ‌های ۱۰٪/۵٪ و ۳۰ روزِ سند، پیشنهاد هستند. در این مرحله مقدار مالی جدید خودکار اعمال نمی‌شود؛ policy باید به تنظیمات تأییدشده متصل و نسخه‌دار باشد. بدون تعریف مشتری جدید، مهلت refund، نرخ/حداقل تسویه و مسئول تأیید، **فعال‌سازی مالی متوقف** می‌ماند؛ توسعه/تست مستقل ادامه دارد.

## ۷. پنل و تنظیمات امن

- در پنل موجود: کمپین/policy، رسانه‌های registry مشترک با منشأ Manus/Zernio/اکتشاف، زبان‌های مجاز، چهار کلیدواژه، هشت متن همکار + متن دوست/لینک، وضعیت دریافت/ارسال، رویدادها/خطاهای غیرحساس و API prompt جدیدِ media-only. سوییچ دستی/عامل و defaultAgentId در DB ذخیره می‌شوند؛ Manus پروفایل اولیهٔ پیش‌فرض است. publishingProvider از adapter/قابلیت معتبر می‌آید؛ تغییر انتخاب فقط برای jobهای جدید و با مجوز ادمین است و مالک job درحال‌اجرا را عوض نمی‌کند.
- Whole Word باید Unicode/locale-aware باشد: فارسی و نیم‌فاصله، حروف ترکی I/ı/İ، انگلیسی و روسی؛ `Ready` با `Already` یا `آماده` با ترکیب نامعتبرِ چسبیده یکی نباشد. انتخاب زبان و duplicate/edit جدا تست شوند.
- پنل Zernio با API ادمین اختصاصی و ذخیرهٔ رمزگذاری‌شده، طبق طرح قبلی؛ **env اولویت دارد**، DB رمزگذاری‌شده fallback صریح. `BAZINO_SECRETS_KEY` خارج DB برای حالت پنل؛ نبود آن فقط ذخیرهٔ امن پنل را متوقف کند، نه receiver مبتنی بر env را.
- `ZERNIO_API_KEY`، `ZERNIO_IG_ACCOUNT_ID`، `ZERNIO_WEBHOOK_SECRET` به سرور محدودند؛ همهٔ مسیرهای عمومی settings/bootstrap/WebSocket/log، aliases و endpoint عمومی ویرایش تنظیمات تست نشت/دورزدن دارند.
- داشبورد همکار تجمیعی و بدون اطلاعات شخصی دوست/تراکنش داخلی؛ داشبورد ادمین/مالی مجوزدار. KPIها از رویدادهای واقعی بیایند، نه صرف وجود ردیف کمیسیون. مقادیر unavailable به‌صورت ناموجود نشان داده شوند، نه صفر یا آمار ساختگی.
- Insights اختیاری با دسترسی معتبر از Zernio، در سطح Media و با کش/فاصلهٔ معقول؛ عدم دسترسی به Insights مانع فلو کامنت/دوست نیست. نسبت‌ها با مخرج صفر `N/A` و روش انتساب Follow شفاف باشد.
- قواعد محتوایی سند (۴ اسلاید tr/fa/en/ru، کپشن ترکی، نسبت Reel، preview و batch سه‌تایی، افشای همکاری) در راهنمای ناشر/metadata و پیش‌نمایش حفظ شوند؛ **این نوبت هیچ محتوا یا پیام انبوهی منتشر نمی‌شود و آداپتور آینده فقط job/نسخه/batch صریحاً مصوب را اجرا می‌کند**. تغییر برند/قالب یا ساخت Meta app مستقیم برای پورتال جزو دامنه نیست؛ مجوزهای حساب متصل و Inbox در Zernio بررسی می‌شوند.

### ۷٫۱ Composer انتشار دستی ادمین — دامنهٔ صریح نسخهٔ ۳

- ابزار مشترک در ContentConsole پنل سایت و نرم‌افزار مدیریت: بارگذاری واقعی تصویر/ویدئو، کتابخانهٔ رسانه، caption چندزبانه، انتخاب حساب مجاز و قالب **تک‌تصویر، Carousel تصویر/ویدئو، Reel و Story در صورت پشتیبانی**؛ هیچ وابستگی به تولید Manus برای ایجاد پست دستی نباشد.
- اسلایدها قابل مرتب‌سازی/حذف/جایگزینی با preview واقعی، thumbnail/پخش ویدئو و کاور مجاز؛ ترتیب payload دقیقاً همان ترتیب UI. کپشن با خط جدید/emoji/hashtag/mention و محدودیت طول قالب، نه وعدهٔ HTML/Markdown یا ویرایشگر گرافیکی/ویدیویی ناموجود.
- upload session مالک‌دار، پیشرفت/لغو/retry، انتقال جریانی/قطعه‌ای برای فایل بزرگ، MIME/حجم/metadata معتبر سمت سرور، quota و عدم ذخیرهٔ اصل فایل در Git/public/dist یا دیسک موقت.
- **اصل رسانه خصوصی و ماندگار** روی storage adapter مناسب/Volume واقعی؛ پیش‌نویس و job با assetId/version/hash کار کنند. مدل تک‌فایل `mediaUrl/mediaType` فعلی با آرایهٔ مرتب assets و مهاجرت سازگار تکمیل شود.
- انتقال به Zernio از `POST /v1/media/presign`، PUT فایل و استفاده از `publicUrl` در `mediaItems`؛ API Key فقط بک‌اند. فایل temp زرنیو منبع دائمی پیش‌نویس نیست: زمان‌بندی طولانی باید از اصل ماندگار نزدیک زمان نشر staging شود، نه از URL منقضی.
- پیش‌نویس → preview → تأیید نسخه → اکنون/زمان‌بندی با timezone صریح. تغییر caption/رسانه/ترتیب/قالب/مقصد، approval را باطل کند. نسخهٔ منتشرشده و سوابق آن با ویرایش draft عوض نشوند.
- Instagram متن‌تنها ندارد؛ Story و رسانهٔ عمومی بدون campaign، خودکار وارد افیلیت نمی‌شوند. قالب چهاراسلایدی/قواعد batch محتوای Affiliate از حالت عمومی جدا و محفوظ‌اند؛ نشر محتوا و اجازهٔ ورود به کمپین دو تصمیم جدا هستند.
- حالت واقعی انتشار همچنان نیازمند کلید/مجوز و تأیید صریح batch است. مستندات نگه‌داری فایل، محدودیت‌ها و تست‌ها: [معماری §۵٫۱](../publishing/ZERNIO_EVENTS_AND_ARCHITECTURE.md).

### ۷٫۲ حالت دستی/عامل و عامل پیش‌فرض Manus — نسخهٔ ۴

- سوییچ مشترک و ماندگار **manual / agent** در پنل سایت و مدیریت؛ دستی = Composer و نشر backend/Zernio بدون فراخوانی Manus، عامل = پروفایل انتخاب‌شده با قرارداد/قابلیت نشر معتبر و approval لازم. انتخاب mode کار اجرا نمی‌کند.
- Agent Registry با نام، adapter/type، credentialRef، capabilities، enabled و configVersion؛ افزودن/ویرایش/فعال‌غیرفعال/انتخاب پیش‌فرض و تست اتصالِ آگاهانه. API Key از فرم اختصاصی به vault سرور می‌رود، نه مرورگر/لاگ/PublicationJob.
- Manus با شناسهٔ ثابتِ built-in و `defaultAgentId` واقعی در DB seed شود؛ فقط در نصب اولیه/فقدان دادهٔ اولیه. انتخاب سفارشی مدیر، rename/disable یا حذف عمدی credential با restart بازنویسی/احیا نشود.
- پیش‌فرض عامل = Manus؛ حالت قبلی مدیر حفظ شود. در نبود حالت ذخیره‌شده، قبل از اولین job مدیر انتخاب کند. بدون کلید، Manus «تعریف‌شده ولی نیازمند پیکربندی» است، نه متصل/آماده؛ Secret ساختگی یا شبیه‌ساز موفق‌نما ممنوع.
- binding کلید موجود Manus (`manus_api_key` و fallback به `MANUS_API_KEY`) در مهاجرت حفظ و منبع آن مشخص شود؛ تقدم env زرنیو به‌صورت کور به Manus تعمیم داده نشود. تفاوت «غایب» با «صریحاً پاک‌شده» حفظ شود تا revoke به fallback پنهان منجر نشود.
- API Key سرویس عامل با توکن scoped `baz_…` اعلام رسانه به backend متفاوت است؛ agent در افیلیت فقط media_id می‌دهد و کد/لینک/Gate/کوپن/کمیسیون همچنان مسئولیت backend است.
- API Key دلخواه به معنی پشتیبانی API هر عامل نیست؛ هر نوع به adapter احراز هویت، task/status/callback و قابلیت‌ها نیاز دارد. Manus نخستین adapter هدف است؛ عامل فاقد پشتیبانی/مجوز publish، ready معرفی نمی‌شود. داده‌های چت/Jarvis خودکار به عامل ناشر ارتقا نیابند.
- snapshot job شامل mode/agentId/agentConfigVersion/provider/owner و approval، بدون Secret؛ تغییر mode یا default، job جاری را کپی نکند. callback دیررس/عامل دیگر، لغو نامطمئن و تعویض کلید بدون overwrite، موفقیت ساختگی و تغییر صاحب کار مدیریت شوند.
- این تنظیم‌ها approval نسخه/batch، اختیار ادمین و محدودیت هزینه/انتشار واقعی را دور نمی‌زنند. جزئیات seed، credential migration و تست‌ها در معماری §۵٫۲ است.

## ۸. بچ‌های اجرای پیشنهادی پس از تأیید

## ۹. معیارهای پذیرش اصلی

1. Manus تنها `media_id` منتشرشده را می‌فرستد و هیچ کد/لینک دریافت نمی‌کند؛ token ناشر عملیات مالی/ساخت دعوت/وب‌هوک جدید را مجاز نمی‌کند.
2. رسانهٔ A ثبت‌شده پردازش می‌شود؛ B ثبت‌نشده، شناسهٔ با prefix مشابه، account دیگر، فیلدهای متعارض و ID گم‌شده، صفر اثر تجاری دارند. ثبت رسانهٔ تازه مجوز قدیمی را خودکار حذف/لغو را دوباره فعال نمی‌کند.
3. رسانهٔ A/B و حساب/کمپین/author اشتباه جای هم نمی‌نشینند؛ اعداد شناسه بزرگ بدون افت دقت حفظ می‌شوند.
4. HMAC نامعتبر/غایب رد، raw body با whitespace معتبر پذیرفته و webhook.test بی‌اثر باشد. نبود Secret/DB، موفقیت کاذب ایجاد نکند.
5. رویداد/کامنت تکراری، تغییر زبان و درخواست‌های موازی روی دو URL، PR/کد/کوپن تکراری نسازند؛ duplicate با body متفاوت تعارض ثبت کند.
6. چهار کلیدواژه به زبان درست، Whole Word، موارد Unicode/ترکی/فارسی و زبان مبهم تست شوند؛ پیام فارسی دوم عین متن منبع با جایگزینی تنها عدد باشد.
7. دکمهٔ همکار/دوست دیگر، payload جعل‌شده، sender ناسازگار، replay یا policy نامعتبر مرحله را جلو نبرد.
8. هیچ خروجی همکار/Manus/کامنت عمومی/log حاوی لینک خصوصی نباشد؛ ورود `invite_url` به قالب همکار رد شود. لینک فقط برای friend معتبر همان referral صادر/ارسال شود.
9. true/false/unknown/خطای Follow تفکیک، `button_event_only` صادقانه و Like checkbox فقط self-attested باشد؛ آمار Share کلی جای مدرک شخصی ننشیند.
10. friend_code همان رسانه/کمپین و شخصی غیر از شریک را لازم داشته باشد؛ کد صادرنشده یا خودارجاعی رد شود.
11. صدور هم‌زمان کوپن دوباره نشود؛ دو دوست یک همکار کوپن مشترک یک‌بارمصرف نداشته باشند؛ owner، تاریخ، policy و محدودیت واقعی checkout اعمال شوند.
12. Gate و اعتبار امضای لینک واقعاً به route/UI وصل باشند؛ query string `gate=1` به‌تنهایی اثبات اجرای Gate نباشد. چرخش Secret وب‌هوک لینک‌های قبلی را ناخواسته باطل نکند.
13. form code معتبر بر آخرین لینک مقدم، انتساب روی سرور و پنجره مصوب باشد؛ رزرو unpaid از Paid/Attended مستقل در KPI ثبت شود.
14. کامنت/Follow/Share/کلیک کمیسیون نسازند؛ paid/session/refund/کارکنان/تکرار و مشتری جدید طبق policy تست شوند. تغییر درصد/مقررات جدید بدون تصویب مالی انجام نشود.
15. از duplicate مالی و PR پس از timeout نامشخص جلوگیری شود؛ pending/lease/restart و محدودیت ۷روز/پنجره DM با ساعت کنترل‌شده تست شوند.
16. هیچ سکرت/لینک خصوصی/PII در API عمومی، پاسخ ادمینِ وضعیت، لاگ، audit یا localStorage ذخیره/نمایش داده نشود؛ نقش‌های غیرادمین API تنظیمات را دور نزنند.
17. سوئیت‌های موجود و تست‌های تازه، TypeScript و build اجرا شوند؛ ۲۲ شکست API قبلی صرفاً از روی گزارش تاریخی بی‌ربط اعلام نشوند و هر نتیجهٔ ناتمام تفکیک شود.
18. Chromium واقعی با فونت فارسی، RTL، چهار زبان، موبایل/دسکتاپ و مشاهدهٔ خود اسکرین‌شات‌ها؛ تست UI داخلی جای آن نیست. اجرای زنده SQL Server/Mongo با contract test یکی اعلام نشود.
19. deployment واقعی و `webhook.test` روی دامنه اثبات شود؛ سبزبودن workflowِ skip/deploy-detach یا داشتن اشتراک در Zernio به‌تنهایی تأیید انتشار نیست.
20. یک رسانه از ingest Manus و نتیجهٔ انتشار Zernio به همان registry/افیلیت برسد؛ حذف Manus منطق partner/friend/coupon/finance را تغییر ندهد.
21. External Posts فقط کشف/به‌روزرسانی وضعیت؛ بدون approval به کمپین راه نیابند. حذف رسانه/قطع حساب، دادهٔ مالی و تعهدات قبلی را پاک نکند.
22. رویداد کل post و per-platform برای همان رسانه duplicate نسازند؛ موفقیت Instagram و شکست مقصد دیگر جدا ثبت شوند و ID بومی با ID داخلی Zernio اشتباه نشود.
23. تغییر ناشر، timeout نامشخص، رویداد دیررس/بی‌ترتیب و post.recycled، انتشار دوم یا عبور از approval ایجاد نکنند.
24. موج external/analytics صف کامنت/دکمه را گرسنه نکند؛ delta cursor بعد از ذخیرهٔ موفق پیش برود و صفحهٔ خالی فوری سبب جاافتادن تغییرات نشود.
25. reaction/referral/read یا نبود delivery receipt، Gate/کلیک سایت/اثبات Like و کمیسیون یا وضعیت تحویل جعلی نسازند. دسترسی Analytics/Publishing با تیک webhook مفروض نباشد.
26. ادمین بدون Manus بتواند فایل واقعی تصویر/ویدئو، caption و قالب انتخاب کند؛ Carousel ترکیبی و ترتیب drag/keyboard دقیقاً در payload/preview حفظ شود.
27. فایل ناقص، MIME جعلی، حجم/codec/نسبت/مدت یا تعداد نامجاز، upload session متعلق به دیگری و URL دلخواه تأییدنشده به انتشار نرسند؛ retry/cancel و فایل قطعه‌ای امن باشند.
28. ماندگاری اصل فایل پس از restart/deploy و زمان‌بندی بیش از هفت روز تست شود؛ URL upload/temp منقضی با restaging از همان اصل حل شود و در نبود اصل، نیاز به upload مجدد صریح باشد.
29. تغییر کپشن/اسلاید/کاور/نوع پست/حساب پس از تأیید، approval را باطل کند؛ دوبارکلیک انتشار یا clone بدون تأیید، پست تکراری نسازد.
30. موفقیت upload/presign موفقیت انتشار شمرده نشود؛ نتیجهٔ هر پست/مقصد در batch و ID بومی قطعی جدا ثبت شود.
31. Story/پست عمومی غیرمتصل به کمپین، عضو خودکار افیلیت نشود؛ متن‌تنها برای Instagram و قالب نامجاز حساب با پیام روشن رد شود.
32. Composer مشترک و پایش upload در Chromium واقعی چهارزبانه/RTL و موبایل/دسکتاپ دیده شود؛ ظاهر/فایل آزمایشی و انتشار واقعی با هم اشتباه نشوند.
33. seed واقعی Manus/defaultAgentId در DB، ماندگاری mode/default با restart و عدم reset انتخاب/disabled/credential پاک‌شدهٔ مدیر تست شود؛ hardcode UI جای رکورد ذخیره‌شده نباشد.
34. تعریف/تغییر عامل و API Key فقط توسط ادمین؛ encrypted credentialRef، ماسک/عدم نمایش مقدار و تست عدم نشت در settings/bootstrap/audit/log/WebSocket/job برقرار باشد.
35. Manus بدون کلید، کلید اشتباه، adapter ناشناخته و عامل فاقد قابلیت نشر، ready/موفق/شبیه‌ساز واقعی معرفی نشود؛ ساخت/انتخاب عامل هیچ تماس یا خرج اعتبار خودکار نکند.
36. mode دستی هیچ تماس Manus نداشته باشد؛ mode عامل از agent انتخاب‌شده استفاده کند، نه hardcode Manus. ناشر فنی و مجوزها با capability همان adapter سازگار باشند.
37. تقدم مؤثر کلید Manus در مهاجرت، تعارض setting/env، نبود کلید اصلی و revoke بدون fallback پنهان تست شوند؛ source انتخاب‌شده بی‌صدا تغییر نکند.
38. سوییچ در draft/generating/approved/submitted، callback دیررس/تکراری/agent اشتباه، لغو نامطمئن و rotation، به overwrite/انتشار دوم/عامل دیگر یا عبور از approval منجر نشود.
39. توکن ingest عامل با API Key سرویسش مخلوط نشود؛ mode عامل دسترسی به لینک خصوصی دوست، Gate/کوپن/مالی یا bypass وب‌هوک ندهد.
40. مدیریت عامل و سوییچ ماندگار در هر دو پنل، چهار زبان/RTL و Chromium واقعی بررسی شود؛ مشاهدهٔ نام Manus، تست اتصال/seed DB محسوب نشود.

## ۱۰. استقرار، پیش‌نیازها و خروج از محدوده

- URL ثبت‌شدهٔ کاربر ثابت: **`https://bazino.pro/api/webhooks/zernio`**. در همان اشتراک `message.received` نیز کنار `comment.received` لازم است؛ وگرنه مراحل «فالو دارم» و DM دوم کامل نمی‌شوند. در این نوبت تنظیم حساب کاربر دست نخورده است.
- سه مقدار Zernio روی سرویس بک‌اند و Secret یکسان در طرف Zernio؛ کلید اصلی رمزگذاری فقط برای حالت پنل. مجوزهای کامنت/پیام و Inbox حساب متصل، و محدودیت‌های واقعی provider پیش از ارسال زنده بررسی می‌شوند.
- حالت انتشار داخلی به API Key مجاز برای publishing و حساب مقصدِ متصل نیاز دارد؛ انتخاب آن اجازهٔ انتشار فوری نیست. برای آمارِ subscription جدا، Secret مستقل پیشنهادی `ZERNIO_ANALYTICS_WEBHOOK_SECRET`/رکورد رمزگذاری‌شدهٔ متناظر، دسترسی Analytics و endpoint مستقر بررسی شود؛ Secret اصلی تغییر نمی‌کند.
- پیش از فعال‌سازی کمپین، ادمین account/campaign/media/languages، متن دوست/لینک و policy Gate را تأیید می‌کند. تنظیمات مالی و مقصد/شرایط کوپن از اطلاعات مصوب سایت، نه وعدهٔ نمونه.
- فرایند موجود Railway/GitHub بررسی و فقط یک مسیر انتشار انتخاب شود؛ commit/push فقط به شاخهٔ جلسه، PR از همان شاخه. push مستقیم به main و تغییر workflow بدون مجوز در این مرحله انجام نمی‌شود؛ در صورت لزوم تغییر workflow، متن کامل آن طبق قاعدهٔ کاربر تحویل می‌شود.
- ابتدا دریافت/آزمایش بی‌اثر، سپس فعال‌سازی کنترل‌شده. آزمایش پیام واقعی فقط به حساب/پست آزمایشیِ مجاز و با اجازهٔ مشخص؛ هیچ تولید/انتشار batch محتوا، مصرف اعتبار یا پیام انبوه از تأیید صرف اسناد برداشت نشود.
- SMTP، POS سخت‌افزاری و درگاه آنلاین خارج از دامنه و متوقف/خاموش می‌مانند؛ روش حضوری نقدی/POS دستی، کیف پول مجاز و سوابق مالی قبلی حفظ می‌شوند.
- ZIP ورودی فقط مرجع قابل اقتباس است؛ ZIP تحویلی تولیدشده خارج Git. داده‌های قدیمی بدون backup/migration و test حذف یا بازنویسی نمی‌شوند.

## ۱۱. شواهد بررسی این نوبت

**افزودهٔ بررسی نسخهٔ ۴:** `ContentService.generate/manusTaskCreate` مستقیماً Manus را انتخاب می‌کند، setting کلید را قبل از env می‌خواند و در نبود آن simulator دارد؛ `ContentItem` فیلد mode/agentId/configVersion ندارد. مدیریت providerهای Jarvis، Agent Registry ناشر نیست. هنوز رکورد seed Manus، defaultAgentId ماندگار، سوییچ یا adapter قابل‌انتخاب در کد محصول ساخته نشده؛ فقط طراحی آن ثبت شد و هیچ کلید واقعی خوانده/ثبت یا اتصال تست نشد.

**افزودهٔ بررسی نسخهٔ ۳:** `shared/management/Content.tsx` فعلاً ایجاد/ویرایش متن دارد، نه file picker/Carousel Composer؛ `ContentVersion` و sanitizer سرور تنها `mediaUrl/mediaType` تک‌مقداری دارند. مسیرهای ماندگار موجود قابل اقتباس‌اند ولی کتابخانه/بارگذاری مدیای Composer هنوز ساخته نشده است. راهنمای رسمی upload خوانده شد؛ نام پارامترهای صحیح، عمر لینک upload/temp و تفاوت سقف upload با محدودیت انتشار در معماری ثبت شدند. تست upload، فایل واقعی، API انتشار یا تغییر هاست این نوبت انجام نشد.

**افزودهٔ بررسی نسخهٔ ۲:** `ContentService.publishOne` در کد فعلی برای سوشیال به URL تنظیم‌شدهٔ webhook POST می‌کند؛ هنوز آداپتور مستقیم چرخهٔ انتشار رسمی Zernio با هم‌بستگی job/per-platform نیست. چک‌کردن گزینه‌های webhook این فاصلهٔ کد را رفع نمی‌کند. جزئیات schema، رویدادهای انتخابی، منابع رسمی و مهاجرت در سند معماری مستقل ثبت شدند.

**یافته‌های ایستا، نه تست‌شده:** مسیر جدید receiver هنوز در محصول ثبت نیست؛ ورودی فعلی `media_type` می‌خواهد؛ keyword تک‌مقداری و زبان caption-based است؛ status ارسال قبل از پاسخ provider تغییر می‌کند؛ مسیر DM و خواندن metadata دکمه نیاز تطبیق دارند؛ کوپن فعلی به partnerCode مشترک است؛ helper امضای لینک یافت شد اما اتصال Gate/اعتبارسنجی آن در مسیرهای سایت در جست‌وجو پیدا نشد؛ پرامپت پنل صریحاً ارسال لینک به شریک را توصیه می‌کند. این‌ها در اجرای پلن اصلاح و با تست اثبات می‌شوند، نه با تغییر متن سند.

مرجع رسمی بررسی‌شده: راهنمای Instagram و Changelog زرنیو برای سقف PR، دکمه و metadata، DM و محدودیت Follow: [2](https://docs.zernio.com/platforms/instagram) [1](https://docs.zernio.com/changelog). صفحهٔ `https://docs.zernio.com/webhooks/inbox` نیز در این نوبت برای envelope و رویدادهای comment/message خوانده شد. استنادهای Meta داخل اصل سند کاربر محفوظ‌اند؛ این نوبت ادعای بازبینی حقوقی همهٔ آن منابع یا تست حساب واقعی نمی‌شود.

**خروجی این نوبت فقط سند منبع + این پلن + به‌روزرسانی وضعیت/هندآف و commit/push است. کد محصول، اشتراک Zernio و هاست تغییر نکرده‌اند.** اجرای کد پس از تأیید/دستور شروع کاربر، با همین تصمیم‌های صریح، آغاز می‌شود.
