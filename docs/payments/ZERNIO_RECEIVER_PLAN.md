## ۲. پاسخ به سؤال مدیریت سکرت‌ها در پنل

**بله، مدیریت سکرت سرویس‌ها از پنل ممکن است و لازم نیست برای تغییر هر API Key به تنظیمات هاست مراجعه شود؛ اما به مسیر اختصاصی امن نیاز دارد.**

وضعیت فعلی بازینو:

- آداپتور `server/affiliate/zernio.ts` متغیرهای Zernio را از env می‌خواند.
- بخشی از سرویس محتوا، `zernio_api_key` را از settings و سپس env می‌خواند؛ در نتیجه یک منبع تنظیمات واحد هنوز وجود ندارد.
- `/api/admin/settings` فعلاً امکان ثبت کلید عمومی دارد؛ `/api/settings` همهٔ کلیدهای خارج از `SECRET_SETTING_KEYS` را به بازدیدکننده برمی‌گرداند. **ثبت دستی `zernio_webhook_secret` در این مسیر فعلی امن نیست**، چون این نام هنوز در فهرست محافظت‌شده نیست. در این نشست چنین مقداری ثبت نشده است.

### طراحی پیشنهادی پنل — محدود به Zernio در این پلن

1. یک بخش «اتصال Zernio» در پنل موجود، فقط برای ادمین مجاز، با API اختصاصی خواندن وضعیت و نوشتن مقدار.
2. فیلدهای API Key، شناسهٔ حساب متصل و Webhook Secret؛ نمایش «تنظیم‌شده/نشده»، منبع مؤثر «هاست/پنل» و زمان تغییر؛ **نه بازگرداندن متن سکرت ذخیره‌شده** به مرورگر.
3. ذخیرهٔ سکرت‌های پنل به‌صورت رمزگذاری‌شدهٔ احرازاصالت‌دار، مثلاً **AES-256-GCM** با nonce تازه و نسخهٔ کلید. شناسهٔ حساب سکرت نیست، ولی تنظیمات اتصال عمومی نمی‌شوند.
4. یک کلید اصلی پیشنهادی به نام **`BAZINO_SECRETS_KEY`** خارج از دیتابیس، در secret manager/محیط هاست نگه داشته شود. رمزگشایی باید سمت سرور باشد؛ hash یک‌طرفه برای API Key قابل استفاده نیست.
5. کلید اصلی هرگز در همان جدول، Git یا localStorage نگه‌داری نشود. در نبود کلید معتبر، ذخیرهٔ سکرت در پنل غیرفعال/خطادار باشد؛ هیچ fallback به متن ساده انجام نشود. بازیابی DB و backup نیز به همان کلید/نسخهٔ محفوظ وابسته است.
6. API عمومی settings، خروجی bootstrap، WebSocket، audit، خطاها و مسیر عمومی ویرایش تنظیمات نتوانند سکرت/کلید رمزگشایی را افشا یا مسیر محافظت‌شده را دور بزنند. audit فقط نام تنظیم/عملیات/عامل/زمان را ثبت کند، نه مقدار.
7. حالت دریافت صرفاً read-only و ارسال واقعی از هم تفکیک شوند؛ «ذخیرهٔ تنظیمات» خودبه‌خود پیام یا پست ارسال نکند. تست ارتباط خارجی فقط با اقدام صریح ادمین و دامنهٔ مشخص انجام شود.

**میزان استقلال از هاست:** همهٔ سکرت‌های سرویس را می‌توان از پنل عوض کرد، اما برای طراحی امن پیشنهادی هنوز یک ریشهٔ اعتماد خارج از DB لازم است. هدف، حذف تنظیم جداگانهٔ هر سکرت روی هاست است؛ نه نگه‌داشتن قفل و کلید رمزگشایی کنار هم در دیتابیس.

### تقدم منابع؛ مطابق درخواست صریح خواندن از هاست

- پیش‌فرض این استقرار: **`ZERNIO_WEBHOOK_SECRET` موجود در محیط هاست منبع مؤثر است**.
- در طراحی دو منبعی، مقدار غیرخالی env اولویت دارد؛ فقط در نبود آن، مقدار رمزگذاری‌شدهٔ پنل استفاده می‌شود. منبع مؤثر در پنل آشکار است و ذخیرهٔ مقدار غیرمؤثر بدون هشدار مجاز نیست.
- برای انتقال بعدی به پنل: مقدار از مسیر امن ثبت و بررسی می‌شود، سپس متغیر مربوط سرویس از هاست حذف و سرویس مجدداً راه‌اندازی می‌شود. پس از آن، تغییرهای عادی از پنل انجام می‌شوند. کلید اصلی رمزگذاری همچنان محفوظ می‌ماند.
- نبود هر دو منبع یا شکست رمزگشایی = اتصال آماده نیست؛ گیرنده هیچ عملیات تجاری انجام نمی‌دهد.
- استفادهٔ مجدد از Webhook Secret برای امضای دعوت‌ها متوقف شود. پیش از تغییر منبع/چرخش، کلید مؤثر دعوت‌های موجود شناسایی و به کلید مستقل تثبیت شود، بدون افشای مقدار و بدون باطل‌کردن ناخواستهٔ لینک‌های قبلی.

## ۳. نشانی‌های پیشنهادی پس از استقرار

گیرندهٔ اصلی برای ثبت در Zernio:

```text
POST https://bazino.pro/api/webhooks/zernio
```

سلامت حداقلی این ماژول، بدون نمایش سکرت یا دادهٔ کاربران:

```text
GET https://bazino.pro/api/webhooks/zernio/health
```

مسیر فعلی نیز برای سازگاری حفظ می‌شود:

```text
POST /api/integrations/zernio/webhook
```

**این‌ها نشانی‌های هدفِ پلن‌اند، نه اعلام استقرار انجام‌شده.** مسیر قدیمی و جدید باید به دریافت/دفتر ثبت مشترک برسند؛ برای یک حساب/کمپین، دو اشتراک Zernio با پردازش مستقل ساخته نشود. مسیر جدید الزام HMAC دارد؛ قرارداد Bearer مسیر قدیمی و APIهای Manus با تست سازگاری حفظ می‌شود و به bypass امضا روی مسیر جدید تبدیل نمی‌شود.

## ۴. مراحل اجرا پس از تأیید

### مرحلهٔ ۱ — ادغام در همان Express، بدون اجرای برنامهٔ دوم

- استخراج انتخابی منطق نرمال‌سازی/پیام/گیرنده، با حفظ منبع فایل‌های ورودی؛ `client/`، `dist/`، OAuth/tRPC/heartbeat/ابزارهای عمومی Manus و package/lock مستقل وارد برنامهٔ بازینو نشوند.
- ثبت مسیر جدید در `server.ts` و ماژول `server/affiliate/`؛ همان دامنه، پورت و فرایند فعلی. `/api/health` کلی سایت بازنویسی نشود.
- parser محدود raw body برای webhook پیش از parser عمومی JSON؛ گرفتن بایت‌های اصلی، نه `JSON.stringify` مجدد. خطاهای اندازه، JSON و async از مسیر خطای کنترل‌شده عبور کنند.
- HMAC-SHA256 و مقایسهٔ زمان‌ثابت، با Secret از resolver مشترک؛ رویداد `webhook.test` بدون هیچ دعوت/پیام/کوپن پاسخ داده شود.
- نام معیار شناسهٔ حساب: `ZERNIO_IG_ACCOUNT_ID`. اگر alias بسته، یعنی `ZERNIO_ACCOUNT_ID`، پشتیبانی شود فقط در نبود مقدار معیار و با وضعیت روشن؛ اختلاف هم‌زمان دو مقدار، خطای پیکربندی است. شناسهٔ هاردکد بسته، مجوز ارسال یا فیلتر پیش‌فرض حساب نیست.

### مرحلهٔ ۲ — داده و پردازش پایدار، روی پرووایدرهای فعلی

- استفاده از `IDataStore`، رکوردهای عملیاتی نسخه‌دار و قید یکتایی موجود برای inbox/outbox؛ reuse داده‌های `ig_media`/`ig_members`/`ig_events` و موتور افیلیت، نه ساخت MySQL/دفتر پورسانت دوم.
- ثبت اتمیک event id، hash بدنه و account؛ تکرار event، رقابت دو درخواست/worker و تغییر بدنه زیر همان ID کنترل شود.
- claim پایدار پیام بر اساس account + commentId، مستقل از نوع پیام؛ فقط یک Private Reply برای هر کامنت.
- درخواست HTTP پس از اعتبارسنجی و ذخیرهٔ پایدار پذیرفته شود؛ worker مشترک، lease و بازیابی پس از restart داشته باشد. اتصال خارجی داخل تراکنش طولانی DB قرار نگیرد.
- timeout پس از ارسال احتمالی به وضعیت «نتیجه نامشخص» برسد؛ پیش از تطبیق، ارسال کور تکرار نشود. ثبت موفقیت فقط با پاسخ معتبر ارائه‌دهنده؛ تضمین غیرواقعی exactly-once برای شبکه داده نشود.
- در نبود دیتابیس، پذیرش موفق کاذب یا ارسال بدون دفتر ثبت ممنوع باشد. raw payload کامل به‌صورت پیش‌فرض آرشیو عمومی نشود؛ فقط دادهٔ لازم و metadata غیرحساس نگه‌داری شود.

### مرحلهٔ ۳ — سازگاری رفتار کمپین و اتصال Zernio

- فیلدهای واقعی webhook، به‌ویژه حساب متصل، پست، کامنت، نویسنده و ID رویداد، با قرارداد رسمی تطبیق داده شوند؛ ID حساب فرستندهٔ بازینو با Instagram user id شریک یا media id اشتباه نشود.
- حالت ZIP: «آماده» → ساخت/بازیابی دعوت از سرویس موجود → PR کد شریک؛ کد عددی توسط **دوست دیگر زیر همان پست مجاز** → PR لینک دعوت. کلیدواژه، پیام‌ها و رسانهٔ هدف از تنظیمات/رکورد معتبر، با پیش‌فرض‌های صریح ZIP و پشتیبانی زبان‌های موجود مدیریت شوند.
- این حالت برای رسانهٔ انتخاب‌شده از حالت قدیمی Friend Gate متمایز شود؛ دو handler برای یک رویداد پیام مستقل نفرستند. حالت قدیمی و قرارداد `partner-invite` بدون تغییر پنهان قواعد پرداخت/کوپن/کمیسیون باقی بمانند.
- درخواست Follow در متن به معنای تأیید آن نیست. گیرندهٔ ZIP به‌تنهایی مجوز صدور کوپن/کمیسیون تازه ایجاد نکند؛ احراز شرایط موجود سایت محفوظ باشد. خودارجاعی به‌عنوان تأیید دوست پذیرفته نشود.
- فراخوانی داخل همین بک‌اند به `createPartnerInvite`، با actor/trace معتبر، جای تماس HTTP به خود سایت را بگیرد. برای این استقرار `BAZINO_PORTAL_API_TOKEN` اضافی لازم نیست؛ API بیرونی Manus حفظ می‌شود.
- قرارداد PR و مسیر DM موردنیاز جریان قدیمی، همراه پاسخ‌ها/خطاهای Zernio تطبیق و تست شوند. گیرنده در آغاز حالت دریافت/تست داشته باشد؛ فعال‌سازی ارسال، یک اقدام آگاهانه و ثبت‌شده باشد.

### مرحلهٔ ۴ — پنل امن تنظیمات Zernio

- افزودن بخش محدود Zernio به پنل موجود، با API ادمین اختصاصی؛ بدون پنل دوم یا عوض‌کردن قالب سایت.
- resolver مشترک برای مصرف‌کنندگان Zernio، منبع env/DB، وضعیت masked و تنظیم حالت دریافت/ارسال؛ هیچ کامپوننتی مستقلاً از محل دیگری سکرت نخواند.
- رمزگذاری سکرت‌های پنل، مسدودکردن ویرایش از مسیر عمومی settings و آزمون نشت؛ نبود `BAZINO_SECRETS_KEY` باید قابلیت ذخیرهٔ رمزگذاری‌شده را متوقف کند، نه اینکه receiver مبتنی بر env را از کار بیندازد.
- نمایش نشانی قابل کپی وب‌هوک، وضعیت پیکربندی و آخرین دریافت/خطای بدون دادهٔ حساس. ایجاد یا تعویض Secret نیازمند هماهنگی همان مقدار در Zernio است؛ صرف ذخیره در بازینو، تنظیم Zernio را تغییر نمی‌دهد.
- این زیرساخت در آینده برای سرویس‌های دیگر قابل استفاده است، اما انتقال تمام کلیدهای Manus/SMS و تغییر آن سرویس‌ها جزو این پلن نیست.

### مرحلهٔ ۵ — تست، تحویل و استقرار واقعی

## ۵. معیارهای پذیرش

1. Secret صحیح از env خوانده شود؛ نبود Secret/کلید رمزگشایی/تنظیمات لازم، عملیات تجاری ایجاد نکند. تفاوت مقدار محیط و پنل، منبع مؤثر روشن داشته باشد.
2. امضای نامعتبر/مفقود روی مسیر جدید `401` بگیرد؛ افزودن Bearer، HMAC مسیر جدید را دور نزند. تغییر whitespace/ترتیب JSON پیش از دریافت، با امضای همان raw body درست بررسی شود.
3. `webhook.test` معتبر، پاسخ موفق با `outboundSent:false` داشته باشد؛ هیچ پیام، کد، کوپن یا اثر تجاری نسازد.
4. رویداد نامرتبط، حساب/پست خارج از دامنه یا شناسهٔ لازمِ مفقود، هیچ ارسال ایجاد نکند.
5. ارسال هم‌زمان رویداد تکراری، یا دریافت از دو URL سازگار، دعوت/پیام تکراری نسازد؛ تعارض ID با hash متفاوت گزارش شود.
6. پردازش ناموفق، قطعی DB، restart و timeout، در وضعیت پایدار و قابل رسیدگی بمانند؛ ارسال خارجی نامشخص کورکورانه تکرار نشود.
7. کد شریک از موتور فعلی بیاید؛ دوست با شریک یکی نباشد؛ همان رسانه/کمپین کنترل شود؛ ادعای تأیید فالو از روی متن ساخته نشود.
8. روی هر کامنت حداکثر یک PR برنامه‌ریزی شود؛ موفقیت پیام با پاسخ معتبر Zernio تطبیق داشته باشد.
9. سکرت‌های جدید در پاسخ عمومی، API خواندن ادمین، لاگ، audit، state، WebSocket و localStorage ظاهر نشوند؛ کارمند بدون مجوز نتواند با API مستقیم آن‌ها را عوض کند.
10. دادهٔ ذخیره‌شدهٔ سکرت در DB رمزگذاری‌شده باشد؛ رمزگشایی با کلید غلط fail closed و تعویض Webhook Secret مستقل از امضای دعوت‌های قبلی باشد.
11. رفتار فعلی سایت/افیلیت/توکن Manus و پنل چهارزبانه با تست رگرسیون حفظ شود. تست قرارداد provider با تست واقعی SQL Server/Mongo اشتباه نشود.
12. انتشار روی دامنهٔ واقعی، نه فقط build یا preview، با شاهد deployment و تست امضاشدهٔ Zernio تأیید شود؛ اگر انجام نشد صریحاً ثبت شود.

## ۶. ورودی‌های لازم و مرز اجرا

- برای حالت هاست: `ZERNIO_API_KEY`، `ZERNIO_IG_ACCOUNT_ID` و `ZERNIO_WEBHOOK_SECRET` روی **سرویس بک‌اند**؛ مقدار Secret باید دقیقاً با subscription زرنیو یکی باشد.
- برای ذخیرهٔ امن از پنل: یک `BAZINO_SECRETS_KEY` معتبر و پایدار در هاست/secret manager. این نام پیشنهادی جدید است و هنوز کد نشده است.
- تعیین رسانهٔ مجاز/کمپین و وضعیت دریافت/ارسال؛ مقادیر ZIP به‌عنوان پیشنهاد مشخص در UI نشان داده شوند، نه fallback دائمی و پنهان.
- دسترسی مجاز به فرایند انتشار هاست یا اقدام مدیر از داشبورد. هیچ credential در چت یا Git درخواست/ثبت نشود.
- خارج از دامنه: سرور مستقل Manus، MySQL جدید، بازنویسی سایت یا افیلیت، فعال‌سازی پرداخت آنلاین، SMTP، سخت‌افزار POS، تغییر قوانین مالی یا ارسال پیام واقعی بدون مجوز.
