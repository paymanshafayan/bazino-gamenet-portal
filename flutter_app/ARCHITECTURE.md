# BAZINO PRO — سند معماری جامع

> این سند جایگزین `ARCHITECTURE.md` قدیمی شده (که فقط یک نسخه‌ی اولیه‌ی سایت Express رو پوشش می‌داد و با تصمیمات فعلی طراحی، مثل قانون «بدون رنگ بنفش»، در تضاد بود).
> این سند **زنده** است: بعد از هر تغییر واقعی در پروژه، بخش مربوطه به‌روزرسانی می‌شود و در انتهای سند در «تاریخچه‌ی تغییرات» ثبت می‌شود.

**آخرین به‌روزرسانی:** شروع بازنویسی کامل — پایه‌ی اولیه بر اساس بررسی کامل کد در تاریخ تحویل زیپ پروژه.

## ۱. معرفی پروژه

**BAZINO PRO** یک پلتفرم جامع مدیریت گیم‌نت است، شامل چهار بخش مجزا در یک مخزن:

| # | بخش | مسیر | نقش |
|---|---|---|---|
| ۱ | سایت/اپ مشتری | ریشه‌ی پروژه (`src/`, `server.ts`) | React 19 + Vite + Express — رزرو، کافه، فروشگاه، تورنومنت، بلاگ، باشگاه مشتریان، چت زنده |
| ۲ | نرم‌افزار مدیریت داخلی | `Management App/Bazino` | React جدا — مدیریت سیستم‌ها/صندوق، بوفه، مشتریان، حسابداری، اپراتورها، رله‌ی سخت‌افزاری |
| ۳ | اپ موبایل | `flutter_app` | Flutter — خروجی فیچر «تولید کد» (پایین توضیح داده شده)، نه پروژه‌ی مستقل توسعه‌یافته |
| ۴ | فیچر تولید کد C# | `server/GameNet.*` + `src/components/CsharpCodeViewer.tsx` + `src/data/csharpCode.ts` / `csharpMvcCode.ts` | یک **ویژگیِ نمایشی/دانلودی داخل خود سایت**، نه یک بک‌اند موازیِ زنده |

## ۲. تصمیمات معماری کلیدی

### ۲.۱ بک‌اند رسمی: Node.js / Express
بعد از بررسی کامل، تصمیم گرفته شد **Node.js + Express (`server.ts` + `server/dataProviders.ts`) تنها بک‌اند رسمی و production پروژه باشد.** دلایل:
- از قبل کار می‌کند: سیستم نصب (installer)، احراز هویت، وب‌سوکت چت زنده، منطق لویالتی/تخفیف پیاده‌سازی شده‌اند.
- یکپارچگی زبان با فرانت‌اند (TypeScript در هر دو سمت)، امکان اشتراک type/interface.
- اسکریپت build ریشه از قبل هم سایت اصلی و هم Management App را در یک پایپ‌لاین می‌سازد.
- هاست فعلی (`*.runasp.net`، متعلق به MonsterASP.NET) از Node.js **و** MSSQL واقعی به‌صورت رایگان پشتیبانی می‌کند — نیازی به تغییر هاست نیست.

### ۲.۲ پوشه‌ی `server/GameNet.*` (ASP.NET Core) — نقش واقعی‌اش چیست
این پوشه **بک‌اند زنده و موازی نیست.** بررسی دقیق نشان داد:
- محتوای فایل‌های `.cs` داخل `server/GameNet.MVC` و `server/GameNet.WebAPI` عیناً به‌صورت رشته‌های هاردکد داخل `src/data/csharpCode.ts` و `src/data/csharpMvcCode.ts` وجود دارند — این‌ها منبع فیچر «نمایش/دانلود کد معادل C#» هستند که در `CsharpCodeViewer.tsx` به کاربر نشان داده می‌شود.
- همین الگو برای `flutter_app` هم صادق است (`src/data/flutterCode.ts` عیناً با `flutter_app/pubspec.yaml` یکی است، حتی با همان نام اشتباهِ `cyber_nexus_app`).
- **یک لایه از خود این کد هم داخلی ناسازگار است:** `GameNet.Core` + `GameNet.Infrastructure` + `GameNet.WebAPI` با هم سازگارند و یک طراحی معتبر و خوب دارند، ولی `GameNet.MVC` به فیلدها/متدهایی ارجاع می‌دهد که اصلاً روی مدل‌های `GameNet.Core.Entities` وجود ندارند (جدول کامل در بخش ۷). یعنی **این پروژه در کلیت خودش کامپایل نمی‌شود** و هرگز به‌صورت یکپارچه اجرا/تست نشده.

**نتیجه:** از این پوشه به‌عنوان **مرجع طراحیِ منطق تجاری** استفاده می‌کنیم (چون `Core`+`Infrastructure`+`WebAPI` قوانین خوبی دارند)، نه به‌عنوان کدی که باید مستقیماً دیپلوی شود. فیچر C# Code Generator به‌عنوان یک ابزار جانبی/مستندسازی برای کاربرانی که می‌خواهند خودشان نسخه‌ی .NET بسازند باقی می‌ماند.

### ۲.۳ سیستم نصب (Installer) و چند-دیتابیسی بودن
سایت یک صفحه‌ی نصب شبیه nopCommerce دارد (`InstallPage.tsx` + `POST /api/install/setup`) که به مدیر اجازه می‌دهد بین SQLite / SQL Server / MongoDB انتخاب کند. طراحی این بخش (وجود لایه‌ی انتزاعی `BaseDataProvider` با پیاده‌سازی جدا برای هر دیتابیس) **درست و قابل نگه‌داشتن است.**

**وضعیت فعلی پیاده‌سازی (مهم):**
- `SQLiteDataProvider`: واقعی، مستقیماً روی `database.json` کار می‌کند. ✅ واقعی
- `SQLServerDataProvider`: **نمایشی است.** فقط لاگ‌های باورپذیر شبیه SQL Server می‌سازد (`SP_CONFIGURE`, `MSSQL Connection Established`, ...) ولی داخلش از `SQLiteDataProvider` استفاده می‌کند و داده واقعاً در همان فایل محلی ذخیره می‌شود. ❌ باید واقعی شود
- `MongoDBDataProvider`: مشابه بالا، کاملاً نمایشی/شبیه‌سازی‌شده. ❌ باید واقعی شود

## ۳. مدل داده (منبع مرجع طراحی: `GameNet.Core.Entities`)

چون طراحی مدل داده در `GameNet.Core` منسجم و کامل است، این مدل به‌عنوان **schema مرجع** برای پیاده‌سازی نهایی روی Node.js در نظر گرفته می‌شود.

| Entity | فیلدهای کلیدی | توضیح |
|---|---|---|
| `User` | `Id(Guid)`, `Username`, `FullName`, `Email`, `PasswordHash`, `Phone`, `GamerTag`, `LoyaltyPoints`, `CreatedAt` | باید حتماً پسورد در قالب **هش‌شده** ذخیره شود |
| `GameSystem` | `Id`, `Name`, `Category(PC/Console/VR)`, `Description`, `HourlyRate`, `IsActive` | سیستم‌های قابل رزرو |
| `Reservation` | `Id`, `UserId`, `GameSystemId`, `StartTime`, `EndTime`, `TotalPrice`, `FinalPaidAmount`, `DiscountCodeId?`, `IsPaid` | باید هم‌پوشانیِ زمانی چک شود |
| `CafeItem` / `CafeOrder` / `CafeOrderItem` | نام، دسته، قیمت، موجودی؛ سفارش با وضعیت `Pending/Preparing/Delivered/Cancelled` | کسر موجودی هنگام سفارش |
| `Accessory` / `AccessoryOrder` / `AccessoryOrderItem` | نام، برند، قیمت، موجودی؛ سفارش با وضعیت `Processing/Shipped/Delivered/Cancelled` | فروشگاه لوازم جانبی |
| `Tournament` / `Team` / `TeamMember` | عنوان، اسم بازی، جایزه، هزینه‌ی ثبت‌نام، ظرفیت، `BracketJson` | تورنومنت و ثبت‌نام تیمی |
| `Article` / `Comment` | عنوان، خلاصه، محتوا، دسته، نویسنده، لایک | بلاگ/اخبار |
| `DiscountCode` | `Code`, `DiscountType(Percent/Fixed)`, `Value`, `MinOrderAmount`, `ExpiryDate`, `MaxUsageCount`, `UsageCount`, `IsActive` | باید همه‌ی این قیدها چک شوند |
| `LoyaltyTransaction` | `UserId`, `Points`, `Description`, `Type(Earned/Redeemed)`, `TransactionDate` | تاریخچه‌ی امتیاز |

## ۴. قوانین منطق تجاری (مرجع نرمال، مستقل از زبان برنامه‌نویسی)

این قوانین باید در بک‌اند Node.js **سمت سرور و بدون اعتماد به داده‌ی کلاینت** پیاده شوند:

1. **لویالتی:** به ازای هر ۱۰,۰۰۰ تومان مبلغ نهاییِ پرداخت‌شده، ۱ امتیاز. تبدیل امتیاز: حداقل ۱۰۰ امتیاز، هر امتیاز = ۱۰۰ تومان تخفیف، کد تخفیف تولیدی حداقل سفارش = ۱.۵ برابر ارزشش، انقضا ۳۰ روز، تک‌مصرفی.
2. **اعتبارسنجی کد تخفیف:** به ترتیب چک شود: کد وجود دارد و فعال است → منقضی نشده → به سقف تعداد استفاده نرسیده → مبلغ سفارش ≥ حداقل مبلغ. محاسبه‌ی درصدی/ثابت، و تخفیف هیچ‌وقت از مبلغ فاکتور بیشتر نمی‌شود.
3. **رزرو:** قبل از ثبت، باید چک شود هیچ رزرو پرداخت‌شده‌ی دیگری برای همان سیستم با بازه‌ی زمانی هم‌پوشان وجود نداشته باشد.
4. **سفارش کافه/فروشگاه:** قبل از ثبت، موجودی هر قلم باید کافی باشد؛ بعد از ثبت موجودی کسر می‌شود؛ امتیاز لویالتی بعد از تکمیل سفارش (بر اساس مبلغ نهاییِ محاسبه‌شده‌ی سرور، نه کلاینت) اعطا می‌شود.

> ⚠️ **وضعیت فعلی در `server.ts`:** بندهای ۱ تا ۴ در حال حاضر یا اجرا نمی‌شوند (رزرو هم‌پوشان) یا از مقادیر ارسالی خود کلاینت (`req.body.totalPrice`, `pointsEarned`, `discountApplied`) استفاده می‌کنند بدون بازمحاسبه‌ی سروری — این یک شکاف امنیتی/منطقی است که باید در فاز پیاده‌سازی برطرف شود.

## ۷. یادداشت فنی: ناسازگاری داخلی `GameNet.MVC`

برای مستندسازی، فهرست دقیق ناسازگاری‌های `GameNet.MVC` با `GameNet.Core.Entities` (که چرا این پروژه کامپایل نمی‌شود):

| MVC انتظار دارد | چیزی که واقعاً در Core هست |
|---|---|
| `GameSystem.IsReserved`, شناسه‌ی `int` | فیلد `IsReserved` وجود ندارد؛ شناسه `Guid` است |
| `DiscountCode.Type`, `.MinOrder`, `.Expiry` (string) | نام واقعی: `DiscountType`, `MinOrderAmount`, `ExpiryDate` (DateTime) |
| `CafeOrder.GamerTag`, `.OriginalAmount`, `.DiscountCodeUsed` | این فیلدها روی `CafeOrder` واقعی وجود ندارند |
| `IReservationService.GetAllSystems()`, `.GetSystemById(int)` | این متدها در `IReservationService` تعریف نشده‌اند |

این جدول صرفاً برای مستندسازی نگه داشته می‌شود؛ اقدام عملی لازم نیست چون `GameNet.MVC` قرار نیست دیپلوی شود.

## ۸. هاستینگ

دامنه‌ی فعلی (`*.runasp.net`) متعلق به سرویس **MonsterASP.NET** است. این سرویس علاوه بر ASP.NET، از **Node.js** و **MSSQL رایگان** هم پشتیبانی می‌کند — بنابراین انتخاب Node.js به‌عنوان بک‌اند رسمی نیازی به تغییر هاست ایجاد نمی‌کند.
