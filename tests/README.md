# مجموعه تست‌های بازینو — Bazino test suite

یک پروژهٔ تست کامل و **بدون هیچ وابستگی جدید** (نه Jest، نه Vitest) که با
`tsx` و ماژول‌های خود Node اجرا می‌شود (تنها افزودهٔ dev، `jsdom` برای رندر
کامپوننت‌هاست). پنج لایه دارد و همه روی کد واقعی پروژه اجرا می‌شوند — نه mock.

```bash
npm test               # اجرای هر پنج لایه + خلاصهٔ کل
npm run test:unit      # فقط منطق خالص
npm run test:db        # فقط دیتابیس
npm run test:providers # فقط پرووایدرها
npm run test:ui        # فقط رابط کاربری
npm run test:api       # فقط end-to-end
npm test -- unit database   # انتخاب چند لایه
```

خروجی رنگی است و گزارش JSON هر لایه در `tests/reports/` نوشته می‌شود
(این پوشه git-ignore است و با هر اجرا از نو ساخته می‌شود).
اگر حتی یک تست شکست بخورد، کد خروجی غیرصفر است — برای CI آماده است.

## لایه‌ها

| لایه | فایل | تعداد | چه چیزی را تست می‌کند |
|---|---|---|---|
| ۱. واحد | `unit.test.mts` | ۵۲ | منطق خالص: sanitize/parse قالب‌ها، رنگ، srcset، ترجمه‌ها |
| ۲. دیتابیس | `database.test.mts` | ۲۶ | `SqliteStore` واقعی روی فایل موقت |
| ۳. پرووایدرها | `providers.test.mts` | ۲۳ | هم‌ترازی SQLServer/Mongo + اجرای Mongo روی درایور قلابی |
| ۴. رابط کاربری | `ui.test.mts` | ۲۸ | رندر واقعی کامپوننت‌ها در jsdom (کلیک، state، fetch) |
| ۵. API | `api.test.mts` | ۹۵ | سرور واقعی روی پورت واقعی، از طریق HTTP |
| **جمع** | | **۲۲۴** | |

پوشش مسیرهای API: **۶۰ از ۸۲** (قبلاً ۳۸).

### ۱. تست‌های واحد (سوئیت ۱–۹)
`sanitizeThemeId`، `extractIdFromCss`، `stripCssComments`، `hasNewFormat`،
`shadeHex`/`hexToRgba`، `buildSampleThemeZip`/`parseThemeZip`،
`getResponsiveSrcSet` و کامل بودن کلیدهای ترجمه.
ماژول `src/themes/index.ts` به CSS و asset وابسته است، بنابراین از طریق
Vite SSR بارگذاری می‌شود (همان الگوی `scripts/verify-themes.ts`).

### ۲. تست‌های دیتابیس (سوئیت ۱۰–۱۶)
هر تست یک فایل SQLite تازه در پوشهٔ موقت می‌سازد: ساخت جدول‌ها،
idempotent بودن مهاجرت `mobileImageUrl`، CRUD، کاربران و امتیاز باشگاه،
موجودی انبار، کوپن‌ها، رزروها و تنظیمات.

### ۳. تست‌های پرووایدر (سوئیت ۳۵–۳۸)
سرور SQL Server یا MongoDB در دسترس نیست، پس این لایه سه کار می‌کند:
هم‌ترازی قرارداد (هر سه کلاس باید همهٔ متدهای `IDataStore` را داشته باشند —
همان چیزی که موقع افزودن قابلیت جدید فراموش می‌شود)، درستی SQL (هر `@param`
باید `.input()` متناظر داشته باشد، تعداد ستون/VALUES بخواند، جدول‌ها
`dbo.`-qualified باشند، هیچ مقداری مستقیم داخل کوئری چسبانده نشود)، و اجرای
واقعی `MongoStore` روی یک درایور قلابی درون‌حافظه‌ای.

### ۴. تست‌های رابط کاربری (سوئیت ۲۸–۳۴)
کامپوننت‌های واقعی داخل jsdom رندر می‌شوند و از طریق همان Vite بارگذاری
می‌گردند که خود اپ استفاده می‌کند (پس alias `react`→`preact/compat` و
import‌های CSS/asset دقیقاً مثل production حل می‌شوند). کلیک، تغییر state،
`useEffect` و فراخوانی API واقعاً اجرا می‌شوند.

**نکتهٔ مهم:** لودر SSR ویت به‌صورت پیش‌فرض نسخه‌های *جدا* از `preact`،
`preact/compat` و `preact/jsx-runtime` می‌دهد؛ نتیجه‌اش خطای مرموز
«Invalid type passed to createElement» و از کار افتادن contextهاست. در
`tests/dom.mts` با `ssr.noExternal` هر سه به یک نسخهٔ مشترک وصل می‌شوند.

### ۵. تست‌های API / end-to-end (سوئیت ۱۷–۳۰)
سرور واقعی (`dist/server.cjs`) در یک پروسهٔ فرزند با `cwd` موقت بالا می‌آید،
پس دیتابیس و پوشهٔ `themes/` هرگز داخل مخزن ساخته نمی‌شوند. اگر `dist/`
موجود نباشد، `npm test` خودش build می‌گیرد.

پوشش: بوت و هدرهای امنیتی، محتوای عمومی، **تحویل تصاویر** (همهٔ تصاویرِ API
باید `200 image/webp` باشند و هیچ‌کدام unsplash نباشند)، ثبت‌نام/ورود/JWT،
کوپن‌ها، سفارش بوفه، رزرو و تمدید، CRUD ادمین (حفظ `mobileImageUrl`)،
نصب/صدور/حذف قالب و جلوگیری از path traversal، چت و مسیرهای متفرقه.

## نکته‌های مهم دربارهٔ رفتار واقعی سرور

این‌ها هنگام نوشتن تست‌ها کشف شد و عمداً به همین شکل تست شده‌اند:

- **`/api/state`** یک blob مبهم برای Management App است (کلید تنظیماتِ
  `managementAppState`) — نه تجمیع داده‌های فروشگاه. تا وقتی چیزی ننویسد
  `null` است، پس round-trip تست می‌شود.
- **`/api/sync/*`** تا وقتی کلیدی تنظیم نشده عمداً باز است (سازگاری با
  کلاینت دسکتاپ هم‌مکان)؛ به‌محض تنظیم کلید، هدر اجباری می‌شود. هر دو حالت
  تست شده است.
- **احراز هویت** با نبودِ توکن به تنظیم مشترک و قدیمی `activeUsername`
  برمی‌گردد؛ کاربر واقعاً ناشناس فقط بعد از logout وجود دارد.
- **`GET /api/articles`** در حالت `sample` همیشه `SAMPLE_ARTICLES` را
  می‌دهد، پس نتیجهٔ ساختِ مقاله از پاسخ خود endpoint نوشتن بررسی می‌شود.

## باگ‌هایی که این مجموعه پیدا کرد

**۱) لو رفتن کلید sync.** `GET /api/settings` عمومی است و
`gamenet_sync_api_key` را برمی‌گرداند — همان کلیدی که `/api/sync/*` را
محافظت می‌کند. فیلترِ موجود فقط کلیدهای Jarvis را حذف می‌کرد. با
`SECRET_SETTING_KEYS` رفع شد.

**۲) باز بودن کامل پنل مدیریت (جدی‌تر).** هیچ‌کدام از ۳۶ مسیر
`/api/admin/*` میدل‌ور احراز هویت نداشتند، و بدتر: `seedMinimal` تنظیم
مشترک `activeUsername` را روی `"admin"` می‌گذارد و `getCurrentUser` وقتی
توکنی نباشد به همان برمی‌گردد — یعنی **هر بازدیدکنندهٔ ناشناس «مدیر» دیده
می‌شد** و می‌توانست لیست کاربران را بخواند یا دیتابیس را ریست کند.

رفع در سه بخش:
- میدل‌ور `requireAdmin` روی `app.use("/api/admin")` — یک نقطهٔ کنترل
  واحد، پس مسیرهای مدیریتیِ آینده هم خودبه‌خود محافظت می‌شوند. عمداً از
  `getCurrentUser` استفاده نمی‌کند (تا از fallbackِ `activeUsername` عبور
  نکند) و نقش را در هر درخواست از دیتابیس می‌خواند تا سلب دسترسی فوری باشد.
- کلاینت وب حالا JWT را ذخیره می‌کند (`src/services/authToken.ts`) و یک
  interceptor آن را روی درخواست‌های same-origin به `/api/**` می‌گذارد، پس
  هیچ‌کدام از ۴۶ فراخوانی موجود لازم نبود دستی تغییر کند.
- `/api/install/setup` حالا توکن برمی‌گرداند تا مدیرِ تازه‌ساخته‌شده بلافاصله
  بعد از نصب پشت در نماند.

سوئیت ۲۷ (`admin access control`) جلوی برگشت هر دو را می‌گیرد: ناشناس
۴۰۱، گیمر عادی ۴۰۳، توکن جعلی ۴۰۱، و مسیر دورزدنِ `activeUsername` هم
جداگانه تست شده است.

**۳) گم شدن بی‌صدای داده روی رکوردهای نمونه.** `resolveSampleById` رکوردی را
برمی‌گرداند که ممکن است فقط در حافظه باشد (داده نمونه). `UPDATE ... WHERE id=?`
بعدی هیچ سطری را عوض نمی‌کرد ولی endpoint همچنان `success: true` می‌داد. نتیجه:
کامنت روی مقالهٔ نمونه، ثبت‌نام تیم در تورنمنت نمونه و check-in رزرو نمونه
**بی‌صدا از بین می‌رفتند**. با helper `ensurePersisted` رفع شد (رکورد نمونه قبل
از UPDATE داخل دیتابیس materialize می‌شود).

**۴) باز بودن `/api/sync/*` روی اینترنت.** وقتی کلیدی تنظیم نشده بود، همهٔ
درخواست‌ها اجازه داشتند — یعنی روی هر دیپلوی عمومی، داده‌های ایستگاه‌ها و
رزروها بدون احراز هویت خوانده می‌شد. حالا بدون کلید فقط درخواست‌های
**همان ماشین (loopback)** مجازند تا کلاینت دسکتاپ hم‌مکان بدون تنظیمات کار
کند؛ هر تماس از بیرون ۴۰۱ می‌گیرد با پیامی که می‌گوید کلید را کجا تنظیم کند.
